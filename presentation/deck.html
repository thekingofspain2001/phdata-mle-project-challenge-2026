    Listings with blanks get turned away

    Problem

    A seller's listing is missing the bathroom count or the plot size. The API rejects the whole request. No price comes back.

    Impact

    Up to 10–20% of live requests stall. The agent phones back, the seller waits, the valuation queue stops.

    Cost

    Every rejected listing is a conversation restarted and a deal delayed. Coverage, not accuracy, is what leaks.

    Add all twelve sizes, divide by twelve. One city-wide number fills every blank. Simple; ignores the house.

    Mean value

    Sort the row, take the middle. Mansions stop skewing the answer. Still one number for all blanks.

    Nearest Neighbor

    Take the 5 nearest sizes; closer homes count more. Each blank gets its own answer from its own street.

    Summary: which value to fill

    Average and middle give every blank one city-wide number. Similar homes answer per street — and on the fields that move price, that measures 8–21% closer.

    What the test actually showed

    How it was tested

    21,613 sales, 15% of every numeric field blanked at random. Mean, median and NN(5) distance-weighted each refilled the blanks; error measured against the values we hid. The seven nullable fields the prediction API accepts, zipcode excluded because it is required and never imputed.

    Accuracy by field

    Field Most accurate Margin
    Bathrooms KNN 13% ahead
    Floors KNN 13% ahead
    Living area KNN 8% ahead
    Bedrooms Mean 6% ahead
    Basement area Mean 2% ahead
    Above-grade area Mean 2% ahead
    Plot size Mean 2% ahead
    Across all seven KNN on 3 of 7 —

    Read honestly: KNN wins bathrooms, floors and living area, and loses on bedrooms and the three area fields. It ships because the three it wins are the ones that move price — not because it won the experiment.

    Faster answers

    What actually changed

    Load once at startup

    Model, features and demographics load into memory when the process starts. No file I/O per request. The reload itself cost 6 ms a call.

    Dropped the debug print

    v1 did print(input_data) on every call. That alone was 28 ms — more than everything else combined.

    async → sync handler

    Plain def runs in the threadpool. Measured on one request: no gain. It stops the loop stalling; it does not add throughput.

    Measured, 100 unseen examples

    Test /predict /predict/v2
    Serial p50 36 ms 10 ms
    Serial p95 49 ms 15 ms
    Serial throughput 26 rps 91 rps
    8 callers, p50 443 ms 96 ms
    8 callers, throughput 18 rps 80 rps

    Median of 3 runs, 100 rows, single machine. Costs priced by subtraction against a v1 copy: commenting out the print drops p50 36 → 13 ms, caching alone barely registers. Concurrency makes both endpoints worse — prediction is CPU-bound, so threads only spread the same work across waiting callers.

    Type hints

    Hints state what each argument and the reply must be. The editor and type checker flag a wrong call before it runs, and FastAPI reads them to build the OpenAPI schema.

    Was

    def predict(home_features):

    Now

    def predict_v2(
    home_features: HomeFeaturesV2,
    request: Request,
) -> PredictionResponse:

    Input validation

    HomeFeatures object

    Input features for home price prediction.

    bedrooms * integer
    bathrooms * number
    sqft_living * number
    sqft_lot * number
    floors * number
    sqft_above * number
    sqft_basement * number
    zipcode * string

    HomeFeaturesV2 object

    Input features for home price prediction v2; non-zipcode fields nullable.

    bedrooms (integer | null)
    bathrooms (number | null)
    sqft_living (number | null)
    sqft_lot (number | null)
    floors (number | null)
    sqft_above (number | null)
    sqft_basement (number | null)
    zipcode * string matches ^\d{5}$

    Same eight fields. Swagger now demands one instead of eight, and every optional field still carries its bounds check.
